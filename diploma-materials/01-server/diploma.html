ВВЕДЕНИЕ

Цифровая трансформация медиапотребления затронула и нишу аниме: зритель всё реже использует физические носители и локальные архивы, предпочитая браузер и мобильные приложения с синхронизацией прогресса. Для разработчика это означает проектирование отказоустойчивого API, способного обслуживать одновременно гостевой просмотр каталога, авторизованную персонализацию и изолированный контур администрирования. Настоящая работа фокусируется исключительно на этих серверных аспектах платформы AniHex.

Японская мультипликация (аниме) за последние два десятилетия превратилась в глобальный культурный и экономический феномен: зрительская аудитория в России и мире ежегодно растёт, появляются легальные и нелегальные каналы распространения, а потребители ожидают от онлайн-сервисов удобного каталога, персонализации и стабильного воспроизведения видео в браузере. Для образовательного коллективного проекта команды разработчиков была поставлена задача создания веб-платформы AniHex, ориентированной на просмотр сериального аниме-контента. Автор настоящей работы отвечал за серверную логику: проектирование API, хранение данных, административный контур и обработку медиафайлов. Клиентская часть (одностраничное приложение) реализована другим участником проекта и в тексте упоминается лишь как потребитель HTTP API.

Актуальность темы обусловлена тем, что современный видеосервис невозможно свести к статическим HTML-страницам: требуется централизованный каталог с метаданными, учёт пользователей, избранное, прогресс просмотра, рейтинги, а также безопасная выдача файлов. На этапе прототипирования допустимо хранение каталога в JSON-файлах, однако для эксплуатации, совместной работы администраторов и целостности связей «тайтл — серия — источник качества» необходимы промышленная СУБД (в проекте — PostgreSQL) и согласованный REST API. Отдельная актуальность имеет административный контур: без него наполнение каталога сводится к ручному редактированию файлов на диске, что неприемлемо для регулярного обновления эпизодов и баннеров главной страницы.

Проблема заключается в отсутствии у учебного проекта единой серверной подсистемы, которая одновременно обслуживала бы публичный каталог, персональные данные зарегистрированных пользователей и изолированный административный доступ с операциями CRUD над контентом и учётными записями, не смешивая привилегии администратора и обычного зрителя. Дополнительная сложность — приём крупных видеофайлов, нормализация формата для веб-плеера и защита от несанкционированного скачивания через API.

Цель работы — разработать и описать серверную логику веб-платформы AniHex для просмотра японских мультипликационных сериалов, обеспечивающую хранение каталога, пользовательские функции и административное управление контентом.

Задачи исследования:

  1. Описать предметную область, проанализировать аналоги и сформулировать требования к информационной системе AniHex.
  2. Спроектировать архитектуру серверного приложения и разделение уровней доступа (публичный, пользовательский, административный).
  3. Разработать реляционную схему базы данных и механизм переключения между PostgreSQL и JSON-режимом для локальной отладки.
  4. Реализовать пользовательское API: регистрация, аутентификация, профиль, избранное, коллекция, прогресс и оценки.
  5. Реализовать административное API с отдельными токенами сессии и полным набором CRUD-операций над каталогом, баннерами и пользователями.
  6. Реализовать загрузку серий и постеров, перекодирование видео средствами ffmpeg и безопасную раздачу медиа.
  7. Провести практическую проверку работоспособности разработанного backend.

Объект исследования — процесс разработки серверной части веб-платформы для потокового просмотра сериального аниме-контента.

Предмет исследования — методы и программные средства построения REST API, хранения данных в PostgreSQL, административного управления каталогом и обработки видео на платформе AniHex.

Методы исследования: анализ научной и отраслевой литературы; сравнительный анализ архитектурных подходов (REST, реляционная модель данных); проектирование структуры данных и интерфейсов API; программирование на платформе Node.js с фреймворком Express; экспериментальная проверка сценариев регистрации, администрирования и загрузки эпизодов.

Практическая база — учебный проект AniHex в репозитории vite-project: каталог server (точка входа index.js, модули store, userStore, auth, adminRoutes, userRoutes, слой db), схема schema.sql, скрипт миграции db:migrate, каталог медиафайлов anime и вспомогательные данные в server/data. Тестирование выполнялось при локальном запуске сервера (npm run dev в каталоге server) с подключением PostgreSQL через переменную окружения DATABASE_URL либо в JSON-режиме без СУБД.

Структура работы. Во введении обоснованы актуальность, цель и задачи. Первая глава описывает предметную область, аналоги, требования, роли и стек. Во второй главе — модель БД и программирование backend и реализация серверной части AniHex. В заключении сформулированы выводы. Приложения содержат фрагменты кода и схемы API.

Научная новизна работы в учебном контексте заключается в комплексном описании и реализации серверной подсистемы именно для аниме-каталога с учётом специфики серий, нескольких качеств одного эпизода, меток опенинга и эндинга, а также жёсткого разделения административного и пользовательского контуров аутентификации в рамках одного Express-приложения. Практическая значимость подтверждается возможностью использовать разработанный API как самостоятельный продукт для наполнения контентом и подключения любого совместимого клиента.

В работе не рассматриваются вопросы вёрстки пользовательского интерфейса, маршрутизации React Router и конфигурации обратного прокси — эти темы отнесены к смежным разделам дипломного проекта команды; для целостности картины достаточно указать, что браузерный клиент обращается к серверу по базовому URL API и получает медиа по маршруту /media.

Материалы работы могут быть использованы при подготовке доклада к защите (см. speech.md в том же каталоге 01-server): тезисы доклада согласованы с главами диплома и отражают вклад автора в серверную часть и административный API. Презентация presentation.html визуализирует архитектуру и результаты; полный текстовый объём раскрыт в настоящем HTML-документе для предоставления комиссии в печатном виде.

ГЛАВА 1. ОПИСАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ

1.1. Идентификация предметной области

Предметная область настоящей работы — веб-платформа для потокового просмотра японских мультипликационных сериалов (аниме) в браузере. Программный продукт AniHex решает задачи централизованного каталога сериального контента, персонализации опыта зрителя и административного наполнения медиатеки без прямого доступа к файловой системе сервера.

Основные функции продукта с точки зрения серверной подсистемы: хранение и выдача метаданных тайтлов и эпизодов; учёт зарегистрированных пользователей (регистрация, сессии, профиль); избранное, коллекция «продолжить просмотр», оценки и прогресс по сериям; административный контур CRUD над каталогом, баннерами витрины и учётными записями; приём и перекодирование видеофайлов; безопасная раздача медиа по HTTP. Эти задачи важны, поскольку зритель ожидает стабильный каталог и синхронизацию прогресса между сеансами, а владелец платформы — регулярное обновление эпизодов без ручного редактирования JSON на диске.

Иерархия данных: «аниме — эпизод — варианты качества (episode_sources)». Удаление тайтла должно каскадно удалять связанные серии и источники. Персональные данные (прогресс, избранное) отделены от канонического каталога: действия зрителя не изменяют общие метаданные тайтла.

Автор работы в командном дипломном проекте отвечает за backend (Node.js, Express, PostgreSQL, REST API, админ-маршруты, обработку видео). Клиентское SPA и контейнерное развёртывание реализованы одногруппниками; в главе 2.3 описано только взаимодействие по HTTP.

1.3. Требования к разрабатываемой информационной системе

Ниже сформулированы функциональные (ФТ) и нефункциональные (НФТ) требования к серверной части AniHex. Требования согласованы с ролью backend-разработчика и покрывают контуры, реализованные в репозитории vite-project.

Функциональные требования:

  1. ФТ-1. Система должна предоставлять публичный REST API каталога аниме (список, карточка тайтла, эпизод, рейтинг).
  2. ФТ-2. Пользователь должен иметь возможность зарегистрироваться, войти, выйти и управлять профилем (настройки, аватар).
  3. ФТ-3. Авторизованный пользователь должен сохранять избранное, коллекцию просмотра и прогресс по сериям.
  4. ФТ-4. Пользователь должен выставлять оценку тайтлу в диапазоне 1–10.
  5. ФТ-5. Администратор должен выполнять CRUD над тайтлами, эпизодами, баннерами главной и учётными записями пользователей через /api/admin/*.
  6. ФТ-6. Администратор должен загружать постеры, видео серий и изображения баннеров (multipart).
  7. ФТ-7. Система должна перекодировать загруженное видео в MP4 H.264/AAC при наличии ffmpeg (опционально).
  8. ФТ-8. Система должна раздавать медиафайлы по /media с защитой от path traversal.
  9. ФТ-9. Прямое скачивание эпизода через API должно быть запрещено (403).

Нефункциональные требования:

  1. НФТ-1. Время отклика GET каталога при работе с PostgreSQL — не более 2 с на учебном наборе данных.
  2. НФТ-2. Пароли пользователей и администратора хранятся в виде хеша (scrypt), не в открытом виде.
  3. НФТ-3. Доступ к административным операциям только при валидном токене с префиксом adm_.
  4. НФТ-4. Целостность данных обеспечивается внешними ключами и CHECK-ограничениями PostgreSQL.
  5. НФТ-5. Конфигурация (порты, DATABASE_URL, пароли) задаётся переменными окружения, не в репозитории.
  6. НФТ-6. Допускается JSON-режим хранения без СУБД для локальной отладки разработчика.

1.4. Определение ролей пользователей программного продукта

Гость (неавторизованный зритель) — посетитель без учётной записи. Возможности: просмотр каталога и карточек аниме, воспроизведение доступных серий, просмотр агрегированного рейтинга; персональный прогресс и избранное — только локально в браузере до регистрации.

Зарегистрированный пользователь — клиент с токеном в user_sessions. Возможности: все функции гостя плюс синхронизация избранного, коллекции, прогресса и оценок с сервером; настройки плеера; загрузка аватара; удаление аккаунта.

Администратор — сотрудник, наполняющий платформу. Возможности: отдельный вход /api/admin/login; CRUD каталога; загрузка видео и постеров; управление баннерами и CMS страницы входа; просмотр и модерация пользователей. Не использует пользовательский токен для привилегированных операций — только adm_.

Разделение ролей на уровне API исключает эскалацию привилегий: middleware requireAdmin и userMiddleware применяются к разным наборам маршрутов.

1.5. Обоснование выбора технологического стека

Тип приложения — веб-приложение: сервер предоставляет REST API и статическую раздачу медиа; клиент — SPA на React (разработка одногруппника). Обоснование: единая кодовая база JavaScript, доступ из браузера без установки клиента.

Язык и фреймворк: Node.js (ES-модули) и Express 5 — асинхронный I/O для одновременных запросов каталога и фонового ffmpeg; зрелая экосистема (multer, pg). Альтернатива Python/Django отклонена из-за разделения стека с frontend-командой.

СУБД: PostgreSQL 16 — реляционная модель с JSONB для жанров и категорий витрины; каскадные FK; драйвер pg. JSON-файлы (library.json, users.json) — режим отладки без DATABASE_URL. Сравнение с MongoDB: для JOIN и ограничений уникальности login/email PostgreSQL предпочтительнее.

Стиль API: REST — предсказуемые CRUD для админки, тестирование через Postman, кэширование GET каталога. GraphQL не внедрялся из-за избыточной сложности для учебного MVP.

Вспомогательные средства: Multer (загрузка файлов), ffmpeg (перекодирование), scrypt (пароли).

2.2. Программирование backend-части программного продукта

2.2.1. Реакция программного продукта на действия пользователей (ответы на запросы)

Выбор Node.js для сервера AniHex обусловлен единым языком JavaScript с клиентской частью проекта, асинхронной моделью ввода-вывода, удобной для одновременной раздачи множества HTTP-запросов каталога и длительных операций перекодирования видео в фоне, а также развитой экосистемой пакетов (express, multer, pg). Express остаётся де-факто стандартом для REST API в Node-сообществе; пятая версия фреймворка использована в проекте с учётом актуальных исправлений маршрутизации.

Серверная часть платформы AniHex (в репозитории модуль server, историческое имя anicatalog-server) построена на Node.js (ES-модули) и Express 5. Точка входа — index.js: инициализация путей к каталогу anime, файлам данных, подключение store, bannerStore, userStore, authPageStore, регистрация маршрутов и запуск прослушивания порта PORT (по умолчанию 3001).

Логически приложение разделено на слои:

  • HTTP-слой — объявление маршрутов, Multer для multipart, обработка ошибок загрузки;
  • Middleware — requireAdmin для админ-токенов; userMiddleware в userRoutes.js для пользовательских токенов;
  • Доменные хранилища — createStore (каталог), createUserStore (пользователи), createBannerStore, createAuthPageStore;
  • Персистентность — при DATABASE_URL модули db/* выполняют SQL; иначе — чтение/запись JSON;
  • Медиа — статическая раздача через /media с функцией isInsideBase против path traversal;
  • Видеообработка — videoTranscode.js, вызов ffmpeg для H.264/AAC MP4.

Маршруты сгруппированы в три контура. Публичный — каталог /api/anime, детали тайтла и эпизода, рейтинг (с опциональным токеном для персонального балла), баннеры /api/home-banners, настройки страницы входа /api/auth-page. Пользовательский вынесен в registerUserRoutes: /api/auth/register, login, logout, /api/user/* (настройки, избранное, коллекция, прогресс, аватар, оценки). Административный — /api/admin/login, session, CRUD аниме, эпизодов, баннеров, пользователей, auth-page; дополнительные маршруты в adminRoutes.js.

Модуль store инкапсулирует операции над каталогом: getAllAnime, getAnimeById, создание и обновление тайтлов, добавление эпизодов, normalizeEpisodeSources для нескольких качеств, setEpisodeDuration при отчёте плеера. bannerStore и authPageStore следуют той же идее единого интерфейса с двумя бэкендами (PG/JSON).

При старте сервера auth.loadSessions() подгружает adm_-токены из admin_sessions или sessions.json. Это позволяет перезапускать процесс без принудительного выхода всех администраторов в PG-режиме (токены персистентны).

Эндпоинт GET /api/health возвращает { ok, admin, name, apiVersion } — диагностика для клиента и админ-панели. Обогащение публичного ответа enrichPublicAnime добавляет вычисляемые поля витрины без раскрытия внутренних путей к необработанным исходникам.

Разделение adminRoutes.js и userRoutes.js улучшает читаемость и сопровождение: изменения в пользовательской политике не затрагивают файл админских маршрутов. index.js остаётся координатором крупных admin-операций с каталогом (создание аниме, загрузка эпизодов, bulk-delete), тогда как adminRoutes.js покрывает пользователей и CMS auth-page.

Каталог server/data в JSON-режиме содержит library.json (структура каталога), users.json, home-banners.json, auth-page.json, sessions.json для adm_-токенов, а также подкаталоги avatars и auth-page для бинарных файлов CMS. Переменная ANIME_DIR указывает корень видеохранилища (по умолчанию ../anime относительно server). Такая файловая организация позволяет разработчику копировать репозиторий и сразу запускать npm run dev без Docker и Postgres, что ускоряет итерации при правке API.

Функция enrichPublicAnime и resolvePublicHomeBanners скрывают от публичного клиента внутренние поля и формируют URL изображений с учётом media_version баннеров для сброса кэша браузера при замене картинки слайда. Это типичный паттерн «тонкий клиент — умный сервер»: клиент не строит пути к файлам самостоятельно.

Модуль episodeSources.js централизует логику нормализации массива sources при создании и обновлении эпизода, а computeWatchStats агрегирует статистику просмотра для отображения в админке или профиле. Вынесение в отдельный файл предотвращает дублирование в нескольких обработчиках POST и PUT.

Пользовательский контур API. Пользовательский контур обслуживает зарегистрированных зрителей. Регистрация POST /api/auth/register принимает login, nickname, email, password, passwordConfirm; при несовпадении паролей — 400. Успешная регистрация создаёт запись в users, выдаёт токен через userStore.issueToken и возвращает publicUser без хеша пароля. Вход POST /api/auth/login проверяет учётные данные; выход POST /api/auth/logout отзывает токен.

Middleware userMiddleware извлекает Bearer-токен, определяет userId, обновляет last_seen_at (touchLastSeen) и отклоняет запрос с 401 при отсутствии сессии. Это стандартная схема для SPA: клиент хранит токен в localStorage или sessionStorage и подставляет заголовок во все защищённые вызовы.

GET /api/auth/me позволяет восстановить сессию при перезагрузке страницы. Настройки: GET и PATCH /api/user/settings. Избранное: GET /api/user/favorites, POST /api/user/favorites/:animeId. Коллекция просмотра объединяет статусы и эпизоды: GET /api/user/collection, POST /api/user/progress для сохранения позиции и флага completed, DELETE для удаления записей. Оценки: GET/POST /api/user/ratings/:animeId с агрегацией на стороне store для публичного /api/anime/:animeId/rating.

Загрузка аватара — POST multipart /api/user/avatar с лимитом размера; DELETE /api/user/avatar сбрасывает изображение. POST /api/user/merge-local переносит данные из локального хранилища браузера после регистрации — важный UX-сценарий, реализованный на сервере для консистентности с БД. Удаление аккаунта DELETE /api/user/account каскадно очищает связанные строки благодаря FK.

Пароли не хранятся в открытом виде: применяется scrypt с солью, сравнение при login через timing-safe подход. Ограничения длины логина и пароля заданы в userStore для предотвращения DoS на хеширование слишком длинными строками.

Публичный каталог остаётся доступен без токена; персонализация (мой балл, избранное) требует авторизации — гибридная модель, типичная для стриминговых сайтов с открытой витриной.

Эндпоинт GET /api/anime/:animeId/rating демонстрирует комбинированную авторизацию: без токена возвращаются агрегированные average и count; с валидным Bearer дополнительно userScore. Реализация не требует userMiddleware, так как отсутствие токена — штатная ситуация для гостя. Это снижает барьер просмотра оценок сообщества до регистрации.

Коллекция просмотра (collection_entries) хранит как привязку к anime_id из каталога, так и локальные поля title и cover для случаев ручного добавления или устаревших ссылок; прогресс по эпизодам в collection_episode_progress содержит last_position_seconds и completed, что позволяет клиенту восстановить воспроизведение с той же секунды на другом устройстве после входа в аккаунт. Сценарий merge-local переносит данные из localStorage нового пользователя, снижая потерю истории при решении зарегистрироваться после пробного просмотра.

Удаление аккаунта и массовая очистка коллекции реализованы отдельными DELETE-маршрутами с явным подтверждением на клиенте; на сервере каскады FK гарантируют удаление favorites, ratings, sessions без ручного перечисления таблиц в коде.

Административный контур API. История принятия решений в команде AniHex включала рассмотрение варианта «админка как набор PHP-скриптов» и варианта «редактирование library.json вручную». Оба отклонены: PHP разрывал единый стек команды, ручное редактирование JSON не масштабировалось при частом добавлении серий и не предоставляло загрузку видео через браузер. Итоговая архитектура — единый Node-сервер с маршрутами /api/admin/* — позволила автору сосредоточиться на одном репозитории и доставлять фичи итерациями (сначала CRUD тайтлов, затем эпизоды и sources, затем пользователи и баннеры).

Как backend-разработчик, автор сознательно выбрал для админ-панели не встроенные формы Express, а REST API с JSON и отдельными административными токенами, поскольку админский интерфейс в проекте — одностраничное приложение, потребляющее те же асинхронные запросы, что и пользовательский сайт. Сервер остаётся единственным местом, где разрешено изменять каталог, загружать бинарные файлы и просматривать персональные данные пользователей в объёме, необходимом модератору.

Вход администратора: POST /api/admin/login с телом { login, password } сравнивает учётные данные с ADMIN_LOGIN и ADMIN_PASSWORD из окружения (в production их необходимо задавать явно). При успехе auth.issueToken() генерирует строку adm_<timestamp>_<random>, сохраняет в памяти Set и в admin_sessions (PostgreSQL) или sessions.json. Клиент сохраняет токен отдельно от пользовательского. GET /api/admin/session под requireAdmin подтверждает активность сессии. POST /api/admin/logout отзывает токен.

CRUD каталога: GET /api/admin/anime — полный список с админскими полями; POST /api/admin/anime — создание; PUT /api/admin/anime/:id — обновление метаданных; DELETE и POST /api/admin/anime/bulk-delete — удаление одного или нескольких тайтлов с очисткой папки на диске. POST /api/admin/anime/:id/poster — загрузка постера (Multer, до 50 МБ). Эпизоды: POST для создания, PUT /api/admin/anime/:id/episodes/:episodeId для метаданных и sources, POST загрузки видео (episodeUpload, лимит до 4 ГБ), DELETE эпизода. После загрузки вызывается compressEpisodeFile → finalizeEpisodeRelativePath с ffmpeg.

Баннеры: GET/POST /api/admin/home-banners, PUT reorder и :id, DELETE, bulk-delete, загрузка изображения слайда. Публичный GET /api/home-banners отдаёт только enabled-слайды в пределах лимита HOME_BANNER_PUBLIC_LIMIT.

Пользователи: в adminRoutes.js — GET список, GET :id деталь, PATCH изменение, DELETE, bulk-delete, сброс аватара. Это позволяет модерировать нарушителей без SQL.

CMS auth-page: GET/PUT /api/admin/auth-page, POST image — настройка брендинга страницы входа.

Обоснование отдельных токенов: администратор никогда не получает user_sessions при работе в админке; компрометация пользовательского токена не даёт права удалять тайтлы. Префикс adm_ упрощает отладку и фильтрацию в логах. Таблица admin_sessions отделена от users — админ может не существовать как рядовой пользователь.

Обоснование CRUD через REST: каждая операция админ-UI сопоставлена одному HTTP-вызову; легко документировать (см. таблицу 3); возможны автоматизированные тесты и скрипты наполнения; единый формат ошибок { error: "..." }. Массовые операции bulk-delete снижают число round-trip при очистке каталога.

requireAdmin подключён ко всем чувствительным маршрутам; пропуск middleware на любом admin-URL считается критической уязвимостью — в коде index.js и adminRoutes.js middleware указан явно на каждом обработчике.

При создании тайтла POST /api/admin/anime сервер генерирует id из названия или принимает явный slug, создаёт папку в ANIME_DIR и запись в anime. PUT позволяет менять описание, жанры, год, тип, season, popularity без повторной загрузки постера. Удаление DELETE дополнительно удаляет каталог с диска через fs.rm, чтобы не оставлять гигабайты «мёртвого» видео. Аналогичная логика применяется к эпизодам: удаление строки в episodes сопровождается удалением файлов sources с диска в пределах папки episodes.

Загрузка фонового видео для карточки тайтла (background_video) и смена постера используют отдельные multipart-эндпоинты с меньшим лимитом размера для изображений (50 МБ) по сравнению с эпизодами (до 4 ГБ), что отражает разную природу медиа. reorder баннеров PUT /api/admin/home-banners/reorder принимает упорядоченный массив id и атомарно обновляет sort_order — важно для drag-and-drop в админ-UI без пересоздания слайдов.

Модуль createAuth в auth.js при PostgreSQL синхронизирует in-memory Set токенов с таблицей admin_sessions при выдаче и отзыве через insertAdminToken и deleteAdminToken, что сохраняет быструю проверку isValid без запроса к БД на каждый HTTP-запрос при небольшом числе активных админ-сессий. При масштабировании на несколько инстансов сервера потребуется либо sticky sessions, либо проверка токена только по БД — это зафиксировано как направление развития.

Детальный разбор типового сценария «добавление новой серии» иллюстрирует взаимодействие компонентов. Администратор авторизуется через POST /api/admin/login и получает adm_-токен. В админ-интерфейсе выбирает тайтл и инициирует создание эпизода: POST с JSON (номер, название, описание, опционально метки OP/ED) создаёт строку в episodes. Затем POST multipart с полем файла отправляет видео на сервер; Multer сохраняет файл в anime/<id>/episodes/; вызывается compressEpisodeFile; по завершении store обновляет episode_sources с путём к MP4 и качеством; публичный GET /api/anime/:id/episodes/:episodeId начинает отдавать sources с URL /media/.... Пользователь открывает серию в плеере, периодически PATCH /api/user/progress сохраняет позицию. Ни один шаг не требует прямого SQL или SSH на сервер — вся цепочка проходит через документированные эндпоинты.

Обработка ошибок в adminRoutes и index.js следует шаблону try/catch с возвратом JSON и логированием неожиданных исключений. Для Multer выделена функция handleMulterError, переводящая код LIMIT_FILE_SIZE в сообщение с указанием мегабайт лимита — важная деталь UX для администратора, загружающего длинные серии в высоком разрешении. Валидация тела запроса минимальна на уровне Express и дополняется проверками в store (существование anime_id, уникальность login при регистрации).

Связь с пользовательским рейтингом: при POST /api/user/ratings/:animeId сервер пересчитывает среднее и количество оценок, доступные через GET /api/anime/:animeId/rating. Агрегация может выполняться SQL AVG/COUNT при PG или перебором при JSON — store скрывает деталь. Это пример того, как бизнес-логика остаётся на сервере, а клиент только отображает числа.

Загрузка видео, тестирование и результаты. Загрузка серии начинается с POST multipart на admin-маршрут с полем файла. Multer сохраняет файл в anime/<animeId>/episodes/ с санитизированным именем. Затем compressEpisodeFile вызывает finalizeEpisodeRelativePath: если включено перекодирование (VIDEO_TRANSCODE или production по умолчанию) и доступен ffmpeg, выполняется конвертация в H.264/AAC MP4 с параметрами CRF и preset из окружения, флагом +faststart для начала воспроизведения до полной загрузки файла клиентом. При отсутствии ffmpeg файл остаётся в исходном формате с предупреждением в лог.

Нормализация episode_sources выполняется в episodeSources.js: администратор может указать несколько качеств; публичный API отдаёт клиенту безопасные URL через /media. Длительность серии может быть определена при обработке и сохранена в duration_seconds; дополнительно клиент может сообщить PATCH /api/anime/.../duration для уточнения статистики watch progress.

Метки opening_start_seconds, opening_end_seconds, ending_start_seconds, ending_end_seconds задаются через admin PUT и используются клиентским плеером — сервер хранит и валидирует числа, не реализуя сам пропуск на backend, что соответствует разделению ответственности.

Раздача статических медиа реализована обработчиком GET с префиксом /media, который сопоставляет запрошенный подпуть с разрешёнными корневыми каталогами. Функция isInsideBase вычисляет path.relative между базой и целевым путём и отклоняет запрос, если относительный путь содержит .. или является абсолютным вне базы. Данный механизм критичен, поскольку URL эпизодов известны клиенту: без проверки злоумышленник мог бы запросить /media/../../etc/passwd в уязвимых конфигурациях. В AniHex используется path.resolve и строгая привязка к ANIME_DIR, BANNERS_DIR, AVATARS_DIR и AUTH_PAGE_MEDIA_DIR.

Безопасность медиа: маршрут раздачи проверяет isInsideBase для каталогов anime, banners, avatars, auth-page; попытка path traversal (../) отклоняется. Прямое скачивание через API отключено сообщением «Скачивание отключено» — снижение риска массового выкачивания контента ботами при сохранении просмотра в плеере.

Методика тестирования. Проверка проводилась вручную с использованием браузерных инструментов разработчика (вкладка Network), REST-клиента и логов консоли сервера. Для каждого контура составлен чек-лист: публичный каталог (список и деталь тайтла, эпизод, баннеры), пользовательский (регистрация с валидными и невалидными данными, login/logout, избранное, прогресс, оценка), административный (login, CRUD тайтла, загрузка постера и эпизода, reorder баннеров, просмотр списка users, удаление тестового пользователя). Отдельно проверялись граничные случаи: запрос admin API без заголовка Authorization; запрос с поддельным токеном usr_ вместо adm_; загрузка файла 0 байт; превышение лимита Multer.

Тестирование. Проверялись сценарии: запуск без DATABASE_URL (JSON) и с PostgreSQL; регистрация и вход пользователя; добавление тайтла и эпизода через admin API; загрузка короткого MP4 с перекодированием; получение каталога GET /api/anime; отказ admin-маршрута без токена (401); отказ /download (403); health-check. Ошибки Multer (LIMIT_FILE_SIZE) обрабатываются handleMulterError с понятным сообщением на русском языке.

Автоматизированные проверки. В репозитории vite-project добавлены модульные тесты на встроенном test runner Node.js: каталог server/tests/ (функции normalizeEpisodeSources, sortSourcesByQuality, computeWatchStats из episodeSources.js). Запуск из корня проекта: npm run test:server или в каталоге server — npm test. Интеграционные сценарии API (регистрация, admin login, загрузка эпизода) по-прежнему проверяются вручную через Postman или браузер; для диагностики доступен GET /api/health (поля ok, apiVersion: 2).

Результаты: реализован работоспособный backend платформы AniHex — REST API версии 2, двухрежимное хранение с приоритетом PostgreSQL, изолированный административный контур с токенами adm_, полный CRUD каталога и вспомогательных сущностей, загрузка и сжатие видео, пользовательские функции личного кабинета. Сервер интегрирован с клиентским приложением одногруппника через согласованные эндпоинты и готов к совместному развёртыванию в составе проекта (инфраструктурная упаковка выполняется отдельным участником и в данной работе не анализируется).

Детализация процесса перекодирования в videoTranscode.js: функция isTranscodeEnabled() читает VIDEO_TRANSCODE или по умолчанию включает сжатие в NODE_ENV=production; hasFfmpeg() кэширует результат проверки наличия бинарника ffmpeg в PATH. processEpisodeVideoFile записывает во временный файл .transcoding.tmp.mp4, затем атомарно заменяет исходник, удаляя не-MP4 оригинал при успехе. Параметры FFMPEG_CRF (по умолчанию 28) и FFMPEG_PRESET (medium) позволяют балансировать качество и время кодирования на слабом сервере разработчика. Флаг +faststart перемещает moov atom в начало файла для прогрессивной загрузки в HTML5 video.

Поддерживаемые входные расширения видео включают mp4, webm, mkv, mov, m4v, avi, ogv — администратор не обязан предварительно конвертировать файл на рабочей станции. Если перекодирование отключено или ffmpeg недоступен, сервер сохраняет исходный файл и регистрирует путь в episode_sources с качеством «Оригинал», что сохраняет работоспособность демонстрации на защите диплома даже без установленного ffmpeg.

Критерии приёмки тестирования включали: корректный JSON и коды ответов; невозможность вызова admin-маршрута с пользовательским токеном; сохранение прогресса просмотра и чтение после повторного login; отображение каталога после добавления тайтла без перезапуска сервера (store перечитывает данные из БД или JSON); отсутствие доступа к файлам вне ANIME_DIR при подстановке ../ в URL /media. Все критерии выполнены на тестовом наборе данных.

Сопоставление с задачами введения: схема данных спроектирована (задача 2–3), пользовательское API реализовано (задача 4), административное API с обоснованием REST и токенов (задача 5), загрузка и ffmpeg (задача 6), проверка работоспособности (задача 7). Теоретический анализ (задача 1) отражён в главе 1.

Конфигурация сервера через переменные окружения (.env) включает: PORT — порт прослушивания; DATABASE_URL — строка подключения PostgreSQL; ADMIN_LOGIN и ADMIN_PASSWORD — учётные данные единственного администратора на этапе MVP; ANIME_DIR — корень видеотеки; VIDEO_TRANSCODE, FFMPEG_CRF, FFMPEG_PRESET — управление перекодированием; NODE_ENV — влияет на включение transcode по умолчанию. Такой подход соответствует двенадцатифакторной методологии (config в среде) и позволяет не хранить секреты в репозитории. userStore и store читают конфигурацию при старте; смена DATABASE_URL без перезапуска не поддерживается — допустимое ограничение учебного проекта.

Слой createStore инкапсулирует различие PG/JSON: вызывающий код в index.js не содержит ветвлений if (postgres) else (file), что упрощает сопровождение. Методы store возвращают объекты JavaScript, сериализуемые в JSON без циклических ссылок. При обновлении эпизода admin PUT нормализует sources через normalizeEpisodeSources, отбрасывая дубликаты качеств и пустые пути — бизнес-правило на сервере, а не на клиенте, что предотвращает порчу каталога ошибочной формой.

Перспектива интеграции с внешними метаданными (базы вроде Shikimori API) могла бы добавить эндпоинт импорта POST /api/admin/anime/import, но в рамках диплома сознательно оставлен ручной ввод, чтобы продемонстрировать полный цикл CRUD и загрузки файлов без зависимости от сторонних сервисов и лимитов их API.

Экономическая эффективность решения для учебной лаборатории выражается в бесплатном стеке (Node.js, PostgreSQL, ffmpeg): отсутствуют лицензионные платежи за сервер СУБД. Трудозатраты backend-разработчика сосредоточены в модулях server/ общим объёмом порядка нескольких тысяч строк кода, что для командного диплома является приемлемым при разделении ролей.

Описание альтернативных архитектур завершает практическую главу. Микросервисное разделение «каталог / пользователи / медиа» для текущего масштаба AniHex избыточно: накладные расходы на сеть и деплой трёх сервисов не окупаются при одной команде и умеренной нагрузке. Монолитный Express с модулями — рациональный выбор. Serverless-функции для загрузки видео ограничены таймаутами и не подходят для перекодирования длинных серий без вынесения в очередь задач; синхронный ffmpeg в обработчике POST приемлем для админской загрузки единичных эпизодов в учебной среде.

Документирование API для команды выполнялось через согласованный перечень маршрутов (таблица 3) и проверку health; формальная OpenAPI-спецификация может быть добавлена в перспективе генерацией из JSDoc или ручным описанием swagger.yaml. Для защиты диплома достаточно приложений с фрагментами кода и примерами JSON-ответов.

Согласованность с кодовой базой: все описанные эндпоинты, таблицы и модули (index.js, userRoutes.js, adminRoutes.js, auth.js, videoTranscode.js, schema.sql) соответствуют состоянию репозитория vite-project на момент написания работы; при эволюции API версия фиксируется полем apiVersion в /api/health. Читатель может воспроизвести описанные сценарии, клонировав репозиторий и выполнив npm install в каталоге server с последующим npm run dev.

Итоговая оценка качества серверной части по критериям полноты, надёжности и сопровождаемости: полнота — реализованы все запланированные контуры API; надёжность — обеспечена на уровне FK, хешей паролей и проверки путей медиа; сопровождаемость — модульная структура server/, единый стиль обработки ошибок, конфигурация через .env. Указанные критерии соответствуют требованиям выпускной квалификационной работы по профилю разработки информационных систем.

2.2.2. Реализация механизмов безопасности и аутентификации

Безопасность API включает: хеширование паролей (в проекте — scrypt через встроенный модуль crypto Node.js); валидацию входных полей (длина логина и пароля); запрет прямого скачивания эпизода через /download (ответ 403); проверку путей при раздаче /media. Принцип наименьших привилегий реализован разделением маршрутов /api/* (публичные и пользовательские) и /api/admin/* (только с requireAdmin).

Пароли не хранятся в открытом виде: применяется scrypt с солью, сравнение при login через timing-safe подход. Ограничения длины логина и пароля заданы в userStore для предотвращения DoS на хеширование слишком длинными строками.

2.2.3. Подключение и управление базой данных

Слой персистентности переключается функцией isPgEnabled() по переменной DATABASE_URL. При подключении PostgreSQL модули db/animePersistence.js и аналоги выполняют параметризованные SQL-запросы через пул pg; при отсутствии СУБД store и userStore читают и пишут library.json и users.json в server/data.

Миграция npm run db:migrate (scripts/migrate-from-json.js) переносит накопленные JSON-данные в таблицы транзакционно. После добавления тайтла через admin API store перечитывает данные из БД — перезапуск сервера не требуется. Проверка появления записей: после POST /api/admin/anime в pgAdmin выполняется SELECT * FROM anime ORDER BY created_at DESC LIMIT 5; после DELETE — строка исчезает, каскад удаляет episodes.

Резервное копирование: pg_dump базы anicatalog и архив каталога ANIME_DIR. Индекс idx_episodes_anime ускоряет выборку серий тайтла.

2.3. Взаимодействие с frontend

Распределение обязанностей: frontend-разработчик (одногруппник) — UI на React/Vite; автор — REST API на порту 3001. Клиент обращается к /api/* и /media/*; в dev Vite proxy перенаправляет запросы на localhost:3001.

Формат обмена — JSON, заголовок Authorization: Bearer <token> для защищённых маршрутов. Пример запроса каталога:

GET /api/anime HTTP/1.1
Host: localhost:3001
Accept: application/json

Пример регистрации (фрагмент клиента userApi.js):

const res = await fetch('/api/auth/register', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ login, nickname, email, password, passwordConfirm }),
});

Ответ сервера: { token, user: { id, login, nickname, ... } }. Админ-клиент использует отдельный токен adm_ для /api/admin/*. CORS настроен для origin dev-сервера Vite.

ЗАКЛЮЧЕНИЕ

В выпускной квалификационной работе решена задача разработки серверной логики веб-платформы AniHex для просмотра японских мультипликационных сериалов. В первой главе описаны предметная область, анализ аналогов, требования к системе, роли пользователей и обоснование технологического стека.

Во второй главе реализована модель базы данных (ER-диаграмма, SQL-запросы, скриншоты СУБД), программирование backend (ответы на запросы, безопасность, управление БД) и взаимодействие с frontend по REST.

Цель работы достигнута. Практическая значимость состоит в том, что разработанный backend может служить основой учебной и коммерчески ориентированной платформы при лицензионном контенте. Направления развития: роли администраторов, журнал аудита, rate limiting, вынесение раздачи видео на CDN, автоматическая проверка длительности через ffprobe при загрузке.

По результатам сравнительного анализа подходов хранения данных для AniHex можно заключить: JSON-файлы пригодны для демонстрации и модульных тестов разработчика, PostgreSQL — для сдачи проекта и дальнейшей эксплуатации; гибридная реализация store с переключением по DATABASE_URL снижает барьер входа команды и не противоречит требованиям надёжности при правильной миграции. Административный API с токенами adm_ доказал удобство при параллельной работе автора backend и разработчика админ-интерфейса: контракт эндпоинтов согласовывался через таблицу маршрутов и проверялся независимо от визуального оформления форм.

В процессе работы автор получил навыки проектирования REST API под реальные сценарии админ-панели, настройки PostgreSQL и согласования схемы с файловым хранилищем медиа, интеграции Multer и внешних утилит (ffmpeg) в конвейер загрузки, а также обеспечения базовой безопасности (хеши паролей, разделение сессий, path traversal). Полученный опыт соответствует профилю подготовки по специальности в области информационных систем и может быть использован при трудоустройстве на позиции backend-разработчика.

Гипотеза работы подтверждена: использование PostgreSQL и раздельного административного API с токенами adm_ повышает надёжность и сопровождаемость платформы по сравнению с монолитным редактированием JSON-файлов. Компромисс JSON-режима для разработки не отменяет ценности промышленной конфигурации с DATABASE_URL при сдаче проекта заказчику или развёртывании на сервере колледжа.

Рекомендации для эксплуатации: задавать сложные ADMIN_PASSWORD и DATABASE_URL в секретах хостинга; включать VIDEO_TRANSCODE в production при наличии ffmpeg; регулярно выполнять резервное копирование БД и каталога ANIME_DIR; мониторить заполнение диска из-за видео; ограничить CORS production-доменом. Рекомендации для разработки: использовать JSON-режим для быстрых правок API, перед демонстрацией заказчику прогонять db:migrate и проверять health. Данные рекомендации вытекают из опыта реализации и тестирования, описанного в параграфе 2.5.

Таким образом, выпускная квалификационная работа представляет собой законченное исследование и практическую реализацию серверной логики платформы AniHex, соответствующую заявленной теме и профилю подготовки, с акцентом на REST API, PostgreSQL, административный контур и обработку видео — без отвлечения на смежные слои клиента и инфраструктуры, что обеспечивает целостность изложения для защиты по направлению серверной разработки.
