## Слайд 2 — Актуальность и проблема

Онлайн-просмотр аниме требует не только сайта, но и надёжного сервера: централизованный каталог, учёт пользователей, безопасная выдача видеофайлов. На этапе прототипа допустимо хранить данные в JSON, но для эксплуатации и совместной работы нужны PostgreSQL и согласованный REST API. Проблема учебного проекта была в том, что не было единой серверной подсистемы с разделением прав администратора и зрителя. Это и определило актуальность моей работы.

## Слайд 3 — Цель, задачи, стек

Цель — разработать серверную логику AniHex. Задачи: спроектировать схему БД; реализовать публичное и пользовательское API; создать административный API с отдельной авторизацией; обеспечить загрузку и перекодирование серий; провести проверку работоспособности. Стек backend: Node.js, Express 5, PostgreSQL, Multer для multipart-загрузок и ffmpeg для нормализации видео.

## Слайд 4 — Объект, предмет и методы

Объект исследования — процесс разработки серверной части веб-платформы просмотра аниме. Предмет — REST API, PostgreSQL, админ-контур и обработка медиа на Node.js. Методы: анализ литературы и аналогов, проектирование реляционной схемы, программирование, экспериментальная проверка сценариев через Postman и логи сервера. Практическая база — каталог `server/` репозитория vite-project.

## Слайд 5 — Архитектура сервера

Точка входа — `server/index.js`. Архитектура построена на Express и слое store: `createStore` для каталога, `createUserStore` для пользователей, отдельные хранилища баннеров и страницы авторизации. При переменной окружения DATABASE_URL данные идут в PostgreSQL; без неё — в JSON для локальной отладки backend. Маршруты разделены на три контура: публичный (каталог, баннеры), пользовательский (регистрация, профиль, избранное) и административный (CRUD контента). Медиафайлы отдаются через `/media` с проверкой, что путь не выходит за каталог ANIME_DIR.

---

## Слайд 6 — База данных PostgreSQL

Схема в `schema.sql` описывает таблицы anime, episodes, episode_sources — каталог и несколько качеств одной серии. Пользователи, сессии, избранное, коллекция и оценки — в отдельных таблицах. Важно: сессии администратора хранятся в admin_sessions, а пользовательские — в user_sessions. Так роли не смешиваются. Для переноса старых данных есть скрипт `npm run db:migrate`. JSON-режим оставлен только для быстрой разработки без установки Postgres.

---

## Слайд 7 — Публичное и пользовательское API

Публичное API отдаёт каталог сайту: GET /api/anime, детали тайтла, баннеры главной. Пользовательское API — регистрация POST /api/auth/register, вход, профиль, избранное, коллекция с прогрессом просмотра. Пароли хешируются scrypt через встроенный модуль crypto Node.js. После входа клиент получает токен с префиксом usr_ и передаёт его в заголовке Authorization: Bearer. Для диагностики есть GET /api/health с полем apiVersion: 2 — клиент может проверить совместимость с сервером.

---

## Слайд 8 — Административное API

Админку я реализовал как REST API, а не как серверные HTML-формы, потому что админ-панель — это SPA, ей нужен JSON. Авторизация администратора — отдельные токены adm_, middleware requireAdmin на всех маршрутах /api/admin/*. Через API выполняются CRUD над аниме, загрузка постеров и серий multipart/form-data, управление баннерами и пользователями. На слайде — скриншоты форм админки: они показывают результат работы API, но сам UI — часть frontend-проекта; в моей работе ключевой результат — контракт endpoints и серверная логика.

---

## Слайд 9 — Загрузка и перекодирование видео

Загрузка серии: клиент отправляет файл → Multer сохраняет во временный каталог → модуль videoTranscode.js вызывает ffmpeg и получает MP4 H.264 с AAC → путь записывается в episode_sources, файл лежит в ANIME_DIR. Так браузерный плеер получает предсказуемый формат, а диск занимает меньше места. Длительность серии определяется для статистики «время просмотра». В админке отображается прогресс загрузки в процентах — это реализовано на клиенте через XHR, а сервер принимает поток Multer.

---

## Слайд 10 — Безопасность серверного API

Основные меры: хеширование паролей; разделение admin и user токенов; middleware requireAdmin; проверка isInsideBase при раздаче /media — защита от path traversal; маршрут прямого скачивания /download возвращает 403; валидация длины логина и пароля. Принцип наименьших привилегий: пользовательский токен usr_ не работает на admin-маршрутах, и наоборот. Это снижает риск эскалации привилегий при компрометации одной сессии.

## Возможные вопросы жюри (краткие ответы)

**Почему PostgreSQL, а не MongoDB?**  
Каталог — связи «аниме — серии — качества — пользователи»; реляционная модель даёт FK и транзакции.

**Почему админ отдельно от пользователя?**  
Разные токены adm_ и usr_, разные таблицы сессий — проще безопасность и аудит.

**Зачем ffmpeg на сервере?**  
Единый MP4 для HTML5-плеера; админ загружает исходник любого формата.

**JSON-режим зачем?**  
Быстрая отладка API без Postgres на машине разработчика.

**Почему не рассказываете про Docker?**  
Контейнеризацию выполнял соавтор; моя работа — прикладная логика и API внутри контейнера api.

**Почему не рассказываете про React?**  
Клиентскую часть для зрителя разрабатывал соавтор; я обеспечил REST-контракт, который клиент потребляет.
