Введение

Стриминговые и каталожные веб-платформы для просмотра японской анимации предъявляют повышенные требования к инфраструктуре: помимо клиентского приложения необходимы сервер API, реляционная база данных, хранение объёмных медиафайлов и стабильная выдача видео в браузере. В учебных и малых производственных проектах разработка часто ведётся на локальных машинах с разными версиями Node.js, PostgreSQL и вспомогательных утилит, что приводит к ситуации «у меня работает», тогда как на другом компьютере или на сервере заказчика развёртывание оказывается затруднённым. Для командной выпускной квалификационной работы, в которой серверная логика и клиентская часть разрабатывались отдельными участниками, критически важен единый воспроизводимый способ запуска всего стека одной командой с сохранением данных между перезапусками.

Актуальность темы обусловлена распространением контейнерных технологий в индустрии разработки программного обеспечения. Docker и Docker Compose позволяют описать окружение декларативно, изолировать зависимости и сократить время передачи проекта от разработки к демонстрации на защите или к эксплуатации на арендуемом VPS. Для медиа-сервисов дополнительную актуальность имеет включение в образ API утилиты ffmpeg для перекодирования загружаемых серий в формат, совместимый с HTML5-видеоплеером, без ручной установки кодеков на хосте. Автоматизация деплоя и документирование процедуры развёртывания снижают операционные риски и делают платформу переносимой между персональным компьютером, учебной лабораторией и облачным сервером.

Проблема заключается в отсутствии унифицированного контура поставки платформы AniHex: до внедрения контейнеризации для запуска требовалось вручную поднимать PostgreSQL, настраивать переменные окружения API, собирать frontend и проксировать запросы к серверу. Пути к каталогу аниме, баннерам и пользовательским медиа различались в зависимости от ОС. При переносе проекта на другой ПК терялись данные, если не копировали каталоги вручную. Наружу не должны были быть опубликованы внутренние порты API и СУБД, при этом пользователю нужен единый адрес сайта (порт 80 или HTTPS на VPS).

Цель работы — спроектировать и реализовать контейнеризацию и автоматизацию деплоя веб-сервиса для просмотра японских мультипликационных сериалов на примере платформы AniHex, обеспечив воспроизводимое окружение, сохранность данных и документированный поток развёртывания.

Для достижения цели поставлены следующие задачи:

  • описать предметную область развёртывания, проанализировать аналоги и сформулировать требования;
  • разработать описание мультисервисного стека в файле docker-compose.yml (сервисы db, api, web);
  • создать Dockerfile для серверного API с поддержкой ffmpeg и multi-stage Dockerfile для статической выдачи frontend через nginx;
  • настроить reverse proxy в deploy/nginx.conf для маршрутизации /api и /media и поддержки SPA;
  • организовать хранение персистентных данных в томах docker-data на хосте;
  • задокументировать переменные окружения, сценарий переноса на другой ПК и краткий порядок развёртывания на VPS в DEPLOY.md;
  • проверить работоспособность полного цикла: сборка образов, запуск, загрузка медиа, перезапуск и перенос данных.

Объект исследования — процессы развёртывания и эксплуатации веб-платформы для просмотра анимационного контента. Предмет исследования — методы контейнеризации, оркестрации сервисов Docker Compose, конфигурации обратного прокси и автоматизации деплоя на примере AniHex. Методы: анализ нормативной и учебной литературы, сравнение подходов к виртуализации и контейнеризации, проектирование инфраструктурной схемы, практическая реализация Dockerfile и compose-манифеста, натурные испытания запуска и переноса томов.

Практическая база — учебный проект AniHex (репозиторий vite-project): каталоги docker-compose.yml, server/Dockerfile, Dockerfile (frontend), deploy/nginx.conf, DEPLOY.md, каталог docker-data для данных вне системы контроля версий. Серверная бизнес-логика и клиентское приложение разработаны соавторами; в данной работе рассматривается исключительно инфраструктурный контур поставки и эксплуатации без детализации React-компонентов и внутренней логики авторизации на уровне исходного кода store.

Структура работы: введение, две главы (теоретическая и практическая), заключение, список источников и приложения. Первая глава — описание предметной области, аналоги, требования, роли и стек. Вторая — автоматизация локального окружения (2.1) и деплой с публикацией (2.2).

Научная новизна работы в учебном контексте состоит в комплексном описании контейнерного контура именно для медиа-ориентированной платформы аниме: учтены тома для крупных видеофайлов, встроенное перекодирование в образ API и согласование с уже разработанным REST-сервером без дублирования прикладной логики в инфраструктурных файлах. Практическая значимость — сокращение времени развёртывания с нескольких часов ручной настройки до нескольких минут автоматизированной сборки, что особенно важно при защите ВКР и при передаче проекта заказчику.

В работе сознательно не анализируются детали React-компонентов, маршрутизация SPA на уровне исходного кода, Zustand-хранилища пользователя и алгоритмы выдачи Bearer-токенов: эти аспекты относятся к смежным частям командного проекта. Упоминание API ограничивается сетевым взаимодействием через /api и /media и требованиями к размеру тела запроса и таймаутам прокси.

Исторически развёртывание веб-приложений проходило этапы: shared hosting с FTP, выделенные серверы с ручной настройкой LAMP/LEMP, виртуальные машины с конфигурационными менеджерами (Ansible, Puppet), затем контейнеры и оркестраторы. Для студенческого проекта средней сложности контейнеры на одном хосте — «золотая середина» между простотой PHP-хостинга и сложностью Kubernetes. AniHex использует ровно этот уровень зрелости.

Экономическая сторона: аренда VPS с 2 vCPU, 4 GB RAM и 40 GB SSD достаточна для десятков одновременных зрителей и фонового ffmpeg при загрузке админом. Контейнеры не добавляют лицензионных затрат (в отличие от некоторых облачных PaaS с помегабайтной тарификацией исходящего видеотрафика). Оптимизация размера файлов через перекодирование снижает расход диска и трафика — инфраструктура и прикладная обработка видео здесь связаны.

Методика выполнения работы включала этапы: анализ предметной области и требований платформы AniHex; изучение документации Docker и Compose; проектирование схемы сервисов и томов; реализация Dockerfile и nginx.conf; итеративная отладка сборки и healthcheck; написание DEPLOY.md; натурные испытания запуска, перезапуска и переноса docker-data; оформление текста ВКР. Каждый этап документировался в репозитории команды, что соответствует требованиям прозрачности выпускной квалификационной работы.

Ожидаемые компетенции по итогам: умение декларативно описать инфраструктуру, понимание сетевой модели контейнеров, навык настройки reverse proxy для SPA и API, понимание персистентности данных вне образов, базовое понимание CI/CD и деплоя на VPS. Перечисленные компетенции востребованы для позиций DevOps-инженера, backend-разработчика с эксплуатационными задачами и системного администратора веб-сервисов.

Границы темы выпускной работы чётко проведены: не рассматриваются алгоритмы рекомендаций контента, дизайн пользовательского интерфейса, детальная модель ролей пользователей и администратора на уровне кода, а также тонкая настройка индексов PostgreSQL — это зона смежных серверных и клиентских работ. Рассматриваются только упаковка готового приложения, сеть между контейнерами, хранение файлов и базы, проксирование HTTP и инструкции эксплуатации.

ГЛАВА 1. ОПИСАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ

1.1. Идентификация предметной области

Предметная область — эксплуатация и доставка веб-платформы AniHex для просмотра аниме: воспроизводимый запуск стека PostgreSQL, API и статики на одном хосте, сохранность медиаданных, единая точка входа для пользователя (HTTP/HTTPS).

Основные функции инфраструктурного контура: контейнеризация сервисов db, api, web; автоматическая сборка образов; обратный прокси nginx; персистентные тома для БД и видео; документированный сценарий локального запуска и переноса на VPS.

Без контейнеризации разработчики сталкиваются с разными версиями Node/Postgres на машинах; compose снимает эту проблему и сокращает время подготовки демонстрации на защите.

1.3. Требования к разрабатываемой информационной системе

Функциональные: запуск всего стека одной командой; сохранение данных при перезапуске; доступ к сайту по одному порту; загрузка видео через админку с перекодированием ffmpeg; перенос окружения копированием docker-data.

Нефункциональные: API и СУБД не публикуются наружу; время старта стека после сборки — минуты; документированный DEPLOY.md; возможность смены WEB_PORT при конфликте порта 80.

1.4. Определение ролей пользователей программного продукта

Разработчик — собирает образы, правит compose и .env.

Администратор контента — наполняет каталог через /admin (клиент соавтора).

Зритель — использует сайт по HTTP; не взаимодействует с Docker напрямую.

Оператор VPS — разворачивает compose, настраивает DNS/TLS и бэкапы.

1.5. Обоснование выбора технологического стека

Тип решения — контейнеризованное веб-приложение на Linux-хосте (VPS или ПК).

Стек: Docker Engine, Docker Compose, образы node:22-alpine и nginx:alpine, PostgreSQL 16, ffmpeg в образе api. Альтернатива Ansible/GitHub Actions описана как этап CI/CD (внедрение в перспективе).

СУБД — PostgreSQL в контейнере db с томом на хосте; схема из server/db/schema.sql.

ГЛАВА 2. ПРОЕКТИРОВАНИЕ И РАЗРАБОТКА ПРОГРАММНОГО ПРОДУКТА

2.1. Автоматизация развёртывания и обновления локального окружения

Ниже приведена детализация реализации compose, Dockerfile и nginx.

Платформа AniHex предназначена для каталогизации и просмотра японских мультипликационных сериалов через браузер. Функциональность реализована в двух прикладных частях (сервер Express и SPA на Vite/React), разработанных соавторами; инфраструктурная часть объединяет их в единый продукт, готовый к демонстрации и переносу. Цели контейнеризации в проекте:

  • одна команда запуска всего стека для проверяющего и членов команды;
  • фиксированные версии PostgreSQL 16, Node.js 22 и nginx Alpine;
  • изоляция API от прямого доступа из сети, вход только через nginx;
  • сохранение видео, постеров, баннеров и базы между пересборками образов;
  • включение ffmpeg в образ API для автоматического перекодирования загружаемых серий в H.264 MP4;
  • формализация инструкции в DEPLOY.md и разделении ролей в команде (сервер/клиент — у соавторов, Docker и деплой — у автора настоящей работы).

Рисунок 1 — Логическая схема контейнерного стека AniHex (описание). Пользователь обращается к хосту по порту WEB_PORT (80). Контейнер web (nginx) отдаёт статические файлы сборки Vite и проксирует запросы /api/* и /media/* в контейнер api:3001. Контейнер api подключается к db:5432 (PostgreSQL), читает и записывает файлы в смонтированные тома docker-data/anime, banners, avatars, auth-page. Контейнер db хранит данные СУБД в docker-data/postgres и при первом запуске выполняет schema.sql из server/db. Вне Docker остаётся только каталог docker-data и исходники в git.

Технологический стек инфраструктуры приведён в таблице 2.

Таблица 2 — Инфраструктурный стек AniHex в Docker

Кросс-ссылка на прикладной уровень: клиентское приложение обращается к API по относительным путям /api и /media, что в production совпадает с origin сайта благодаря nginx; детали реализации UI и хранилища состояния клиента в работе не рассматриваются.

Разделение на три контейнера обосновано границами масштабирования и обновления. База данных обновляется редко и требует осторожных миграций; API обновляется при изменении бизнес-логики и зависимостей Node; web обновляется при каждой пересборке интерфейса. Единый «монолитный» контейнер упростил бы compose-файл, но усложнил бы сопровождение: пересборка фронта потребовала бы перезапуска Postgres. Паттерн «sidecar» здесь не применяется; ffmpeg встроен в api, так как перекодирование неразрывно связано с загрузкой серий на API.

При демонстрации на защите рекомендуется заранее подготовить том docker-data с одним тайтлом и серией, чтобы комиссия увидела воспроизведение без ожидания кодирования. Время первого ffmpeg-перекодирования зависит от CPU хоста и FFMPEG_PRESET; на слабом ноутбуке допустимо временно выставить preset=veryfast или отключить VIDEO_TRANSCODE для показа UI.

Команда docker compose up -d --build является основной «точкой входа» для автоматизации: флаг -d запускает демоны в фоне, --build гарантирует актуальность образов api и web после изменений в Git. Без --build при изменении только server/ можно выполнить compose build api && compose up -d api для точечного обновления. Документирование этих вариантов в DEPLOY.md помогает соавторам не пересобирать лишний раз тяжёлый frontend при правках API. Это завершает описание практической архитектуры стека.

Файл docker-compose.yml в корне репозитория является центральным артефактом автоматизации деплоя. Комментарии в файле указывают команду запуска docker compose up -d --build и URL http://localhost. Сервис db использует официальный образ PostgreSQL 16 на Alpine — минимальный размер при полной функциональности СУБД. Переменные POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB заданы значением anicatalog для согласованности с DATABASE_URL API.

Тома db:

  • ./docker-data/postgres → /var/lib/postgresql/data — персистентный кластер;
  • ./server/db/schema.sql → /docker-entrypoint-initdb.d/01-schema.sql:ro — скрипт создаёт таблицы при первой инициализации пустого тома (повторный запуск на существующих данных скрипт не дублирует).

Healthcheck с pg_isready -U anicatalog -d anicatalog, интервал 5 с, retries 10, даёт compose сигнал готовности. Сервис api собирается из контекста . с dockerfile server/Dockerfile. depends_on db с condition service_healthy исключает гонку старта. environment задаёт production-режим, PORT 3001, DATABASE_URL с хостом db, ANIME_DIR /data/anime, параметры транскодирования и учётные данные админки через подстановку из .env: ADMIN_LOGIN, ADMIN_PASSWORD, VIDEO_TRANSCODE, FFMPEG_CRF, FFMPEG_PRESET.

Тома api связывают контейнерные пути с хостом:

  • docker-data/anime → /data/anime (видео серий и постеры);
  • docker-data/banners, avatars, auth-page → соответствующие каталоги под /app/data/...

expose: '3001' оставляет порт доступным в сети compose без публикации на 0.0.0.0 хоста — снижение поверхности атаки. Сервис web собирается из корневого Dockerfile, depends_on api, публикует ${WEB_PORT:-80}:80. Пользователь видит единый сайт; загрузка видео в админке идёт через nginx с увеличенным лимитом тела запроса.

Последовательность холодного старта: создание сети → старт db → инициализация БД (если том новый) → healthcheck OK → старт api → старт web → nginx слушает 80. Остановка docker compose down не удаляет тома bind-mount на хосте — данные сохраняются. Для полного сброса БД требуется удалить docker-data/postgres осознанно.

Миграция с локального JSON-хранилища (режим разработки без Docker) на PostgreSQL в контейнере документирована в DEPLOY.md: docker compose exec api node scripts/migrate-from-json.js — исполнение скрипта внутри уже запущенного контейнера api с доступом к db по внутренней сети.

Рассмотрим пошагово обработку HTTP-запроса в развёрнутом стеке. Пользователь открывает главную страницу: запрос GET / попадает в контейнер web, nginx находит index.html в dist, отдаёт SPA. Запрос GET /api/anime (пример) — location /api/ проксируется на api:3001, Express обрабатывает маршрут и обращается к PostgreSQL по DATABASE_URL. Запрос GET /media/.../episode.mp4 — прокси на api, отдача файла с диска ANIME_DIR внутри тома. Загрузка POST multipart админкой — тело до 512 МБ принимается nginx, передаётся api, сохраняется в том anime, запускается ffmpeg. Все шаги происходят без публикации порта 3001 на интерфейсе хоста.

Переменная NODE_ENV=production в api отключает dev-инструменты и влияет на поведение isTranscodeEnabled (по умолчанию транскодирование включено в production). restart: unless-stopped обеспечивает подъём контейнеров после перезагрузки сервера VPS при условии, что служба docker настроена на autostart. На Windows Docker Desktop поведение аналогично для локальной разработки.

Сравнение с «docker run вручную» без compose: пришлось бы вручную создавать сеть, запускать postgres с -v, ждать готовности, запускать api с --link или пользовательской сетью, затем web с -p 80:80. Compose сокращает это до декларативного файла из примерно шестидесяти строк, что снижает риск ошибки порядка запуска и забытых томов.

server/Dockerfile начинается с FROM node:22-alpine. Строка RUN apk add --no-cache ffmpeg устанавливает бинарник перекодирования в образ — на хосте разработчика ffmpeg не обязателен при работе только через Docker. WORKDIR /app. Копируются package.json и lock-файл, выполняется npm ci --omit=dev с fallback npm install --omit=dev для устойчивости. Копируется каталог server/ и authLimits.js в корень образа (общий модуль лимитов). RUN mkdir -p создаёт точки монтирования томов. ENV задаёт production, PORT, ANIME_DIR, VIDEO_TRANSCODE=1, FFMPEG_CRF=28, FFMPEG_PRESET=medium по умолчанию. EXPOSE 3001, CMD ["node", "index.js"].

Логика перекодирования на стороне API (модуль videoTranscode.js) при включённом VIDEO_TRANSCODE вызывает ffmpeg с libx264, preset и crf из окружения, аудио AAC, faststart для стриминга в браузере. Если ffmpeg в контейнере недоступен, файл сохраняется без перекодирования с предупреждением в лог — в собранном образе AniHex ffmpeg присутствует по Dockerfile.

Корневой Dockerfile (frontend) — двухстадийная сборка. Стадия build: node:22-alpine, npm ci, копирование исходников, npm run build → каталог dist. Стадия runtime: nginx:alpine, копирование deploy/nginx.conf в /etc/nginx/conf.d/default.conf, копирование dist в /usr/share/nginx/html. EXPOSE 80, CMD nginx в foreground. Итоговый образ не содержит Node на runtime — только nginx и статику, что соответствует best practice для SPA.

deploy/nginx.conf настраивает server на listen 80, client_max_body_size 512m, gzip для текстовых и JSON типов. location /api/ проксирует на http://api:3001/api/ с таймаутом чтения 300 с (загрузки). location /media/ — proxy_buffering off и read_timeout 3600 с для отдачи видео. location / — try_files для SPA. Имена api и web — DNS в compose-сети.

Такое разделение Dockerfile отражает разделение обязанностей: API-образ тяжелее из-за Node и ffmpeg; web-образ легче и оптимизирован для отдачи статики и прокси. Пересборка web требуется при изменении клиента; пересборка api — при изменении server/; db обновляется сменой тега образа postgres при плановом апгрейде СУБД.

Детализация multi-stage frontend: на стадии build копируется весь контекст проекта (включая src и public), выполняется npm run build, Vite формирует dist с хешированными assets. На стадии runtime в nginx попадает только dist и nginx.conf — исходники React и devDependencies не входят в финальный образ, что сокращает размер с сотен мегабайт до десятков. Кэш слоя npm ci на build-стадии ускоряет повторные сборки при изменении только нескольких компонентов, если package.json не менялся.

В server/Dockerfile копирование authLimits.js из корня репозитория в /authLimits.js отражает общую зависимость лимитов запросов между корнем и server — контекст сборки выбран корнем (.), чтобы один Dockerfile имел доступ и к server/, и к этому файлу. WORKDIR /app и CMD node index.js соответствуют структуре package.json сервера.

Конфигурация gzip в nginx сжимает JSON ответов API и JS/CSS статики, экономя трафик на VPS с лимитированным каналом; видео /media/ не сжимается gzip (бинарный поток). proxy_read_timeout 300 с для /api/ предотвращает обрыв долгой загрузки админом; 3600 с для /media/ допускает просмотр длинных серий без idle timeout на прокси.

Альтернатива nginx — встроенный статический сервер Node или Caddy с автоматическим HTTPS. Выбор nginx обусловлен индустриальным стандартом, знакомством по учебной литературе и минимальным Alpine-образом. Traefik мог бы терминировать TLS внутри compose, но для ВКР достаточно схемы «nginx в web + Certbot на хосте».

Каталог docker-data/ намеренно исключён из git: в нём живут эксплуатационные данные. Структура документирована в DEPLOY.md (таблица 3).

При загрузке серии через административный API файл попадает в смонтированный том anime; API выполняет перекодирование в контейнере, уменьшая размер и обеспечивая совместимость с HTML5. Параметры качества/скорости кодирования настраиваются без пересборки образа:

  • VIDEO_TRANSCODE — 1/0 включение (по умолчанию 1 в compose);
  • FFMPEG_CRF — Constant Rate Factor (по умолчанию 28: больше — меньше файл);
  • FFMPEG_PRESET — скорость кодирования (medium по умолчанию);
  • ADMIN_LOGIN, ADMIN_PASSWORD — учётные данные входа в админку (не хранятся в образе, переопределяются через .env);
  • WEB_PORT — внешний порт сайта при занятости 80.

Файл .env в корне проекта (опционально) читается Compose автоматически. Рекомендуется cp server/.env.example server/.env для локальной разработки без Docker; для Docker достаточно compose и корневого .env. DATABASE_URL внутри compose задан явно — не требует правки на типовом запуске.

Переносимость: сценарий «другой ПК» — копировать весь репозиторий и папку docker-data целиком, установить Docker Desktop или Engine, выполнить docker compose up -d --build. Без docker-data сайт поднимется пустым (чистая schema.sql создаст структуру БД). Сценарий «VPS» — git clone + rsync docker-data + .env с сильными паролями + compose up + Certbot для HTTPS. Портативность обеспечивается тем, что пути внутри контейнеров фиксированы (ANIME_DIR=/data/anime), а хост лишь монтирует локальные папки.

Режим локальной разработки без Docker (описан в DEPLOY.md для полноты документации) сохраняет альтернативу соавторам: npm run dev для фронта и server, JSON-файлы при отсутствии DATABASE_URL. Продакшен-контур ВКР — Docker; сравнение подчёркивает ценность единого compose для сдачи и демонстрации.

Алгоритм перекодирования в контейнере (модуль videoTranscode.js) при получении файла проверяет расширение (.mp4, .mkv и др.), флаг VIDEO_TRANSCODE и наличие ffmpeg. Запускается процесс с параметрами -c:v libx264, -crf из FFMPEG_CRF, -preset из FFMPEG_PRESET, -c:a aac, movflags +faststart для оптимизации потоковой отдачи. Временный файл .transcoding.tmp.mp4 предотвращает отдачу недописанного видео. После успеха исходник может быть удалён, каталог остаётся в томе anime на хосте. Администратор на VPS мониторит место на диске: CRF 28 — компромисс качества и размера; снижение до 23 улучшит картинку, увеличив объём.

Переменные ADMIN_LOGIN и ADMIN_PASSWORD не следует оставлять по умолчанию (admin/1111) на публичном VPS. Рекомендация DEPLOY.md — задать в .env и не коммитить файл. .gitignore проекта должен включать .env и docker-data/ — иначе риск утечки медиа и паролей в публичный репозиторий. Для дипломной демонстрации на localhost дефолты допустимы.

Сценарий отказоустойчивости на одном хосте: при падении api compose перезапустит контейнер (restart policy); nginx вернёт 502 до восстановления — пользователь видит ошибку прокси, данные в postgres не повреждаются. При повреждении тома postgres восстановление из бэкапа docker-data/postgres или pg_dump. Сценарий «перенос на другой ПК» проверялся копированием папки: на новой машине идентичные URL и контент каталога без повторной загрузки видео.

2.2. Деплой, эксплуатация и публикация

Развёртывание production-ready приложения: принципы 12-factor (конфиг в env, данные в томах), nginx как reverse proxy, мониторинг через docker compose logs и df -h. Публикация: локально http://localhost; на VPS — DNS, HTTPS (Certbot). Ссылки на работающий продукт приводятся на защите. Перспектива: GitHub Actions, Ansible.

Файл DEPLOY.md — руководство по эксплуатации для команды и проверяющих. Раздел «Как устроено хранение» согласован с томами compose. Раздел «Запуск» содержит команды cp server/.env.example server/.env и docker compose up -d --build, URL сайта и админки /admin/login. Раздел «Перенос на другой ПК» формализует два шага копирования (код + docker-data). Таблица переменных окружения дублирует и расширяет compose-дефолты. Указаны роли участников: сервер и веб — один соавтор, Docker и деплой — автор инфраструктурной части. Краткий подраздел VPS перечисляет: установка Docker, клон + данные, compose up, домен и HTTPS, бэкапы.

Поток развёртывания (deploy flow) можно представить следующей последовательностью:

  1. Клонирование репозитория с Git (или копирование архива).
  2. Подготовка docker-data (пустая или с бэкапа).
  3. Настройка .env при необходимости (пароль админки, WEB_PORT).
  4. docker compose up -d --build — сборка образов api и web, pull postgres, создание контейнеров.
  5. Проверка http://localhost, вход в админку, тест загрузки серии (ffmpeg в логах api).
  6. Для VPS: открытие порта 80/443, DNS, Certbot, настройка firewall, регламент pg_dump и архивации docker-data.

Результаты практической части: платформа поднимается одной командой; окружение идентично на Windows/Linux/macOS с Docker; данные переживают docker compose down и обновление образов; API недоступен напрямую снаружи; nginx обеспечивает единую точку входа и крупные загрузки; DEPLOY.md снижает порог входа для не-инфраструктурных разработчиков; стек готов к размещению на VPS с минимальными дополнениями (TLS, секреты).

Ограничения и перспективы: один хост Compose не масштабирует api горизонтально; секреты в .env на VPS следует ограничить правами chmod 600; для промышленного CI целесообразно добавить GitHub Actions с push в registry и автоматическим deploy. В рамках ВКР реализован воспроизводимый учебно-производственный контур, достаточный для защиты и пилотной эксплуатации каталога аниме.

Испытания выполнялись на локальном компьютере: проверены healthcheck БД, проксирование /api/health или аналогичных маршрутов, отдача статики, монтирование томов после перезапуска, перенос папки docker-data на вторую машину (симуляция переносимости). Ошибки сборки устранялись актуализацией lock-файлов и контекста COPY в Dockerfile.

Развёртывание на VPS по шагам (практическая инструкция, согласованная с DEPLOY.md). Шаг 1: аренда VPS (Ubuntu 22.04 LTS), открытие портов 22, 80, 443 в security group. Шаг 2: установка Docker по официальной документации (apt install docker.io или convenience script). Шаг 3: добавление пользователя deploy в группу docker. Шаг 4: git clone репозитория в /opt/anihex. Шаг 5: rsync/scp docker-data с машины разработки или старт с пустыми томами. Шаг 6: создание .env с ADMIN_PASSWORD и при необходимости WEB_PORT. Шаг 7: docker compose up -d --build, проверка curl http://127.0.0.1. Шаг 8: A-запись DNS на IP VPS. Шаг 9: certbot --nginx -d example.com для TLS. Шаг 10: cron для tar czf бэкапа docker-data и pg_dump. Данная последовательность не требует установки Node и Postgres на хост — только Docker, что и является целью контейнеризации.

Взаимодействие с работой соавтора (сервер): schema.sql и код API разрабатывались без привязки к Docker, но пути ANIME_DIR и DATABASE_URL спроектированы совместимы с compose. Взаимодействие с работой соавтора (клиент): сборка Vite не меняется; в Docker добавляется только стадия nginx. Автор инфраструктурной части не дублировал CRUD и авторизацию, а обеспечил среду их выполнения.

Критерии приёмки инфраструктуры для ВКР: (1) docker compose up -d --build завершается без ошибок; (2) http://localhost открывает каталог; (3) админка доступна по /admin/login; (4) загрузка серии создаёт файл в docker-data/anime; (5) docker compose down && up сохраняет данные; (6) DEPLOY.md позволяет третьему лицу повторить запуск. Все критерии выполнены.

Сравнение трудозатрат: ручная установка Postgres + Node + nginx на Windows и Linux различалась инструкциями; compose сократил документацию до одного файла DEPLOY.md и одного YAML. Время первой сборки образов (npm ci, vite build) — несколько минут на SSD; последующие up — секунды. Экономия достигается при N>1 развёртываний (члены комиссии, соавторы, VPS).

Описание ключевых фрагментов манифеста для приложений (Приложение А). Сервис db задаёт image: postgres:16-alpine и монтирование schema.sql — связь инфраструктуры с серверной схемой данных. Сервис api содержит build.context: . и dockerfile: server/Dockerfile — единый репозиторий для команды. Сервис web публикует порт через ${WEB_PORT:-80}:80 — параметризация без редактирования YAML. Директива depends_on с condition: service_healthy — современный синтаксис Compose v2, заменяющий устаревшие скрипты wait-for-it.sh.

Перспектива использования образов из registry: после CI образы ghcr.io/org/anihex-api:tag и anihex-web:tag могут подставляться в compose через image: вместо build: для ускорения deploy на VPS без npm на сервере. Текущая практика проекта — build на месте, что проще для учебного репозитория без настройки registry.

Экологичность и ресурсы: один хост с тремя контейнерами потребляет меньше RAM, чем три ВМ. ffmpeg нагружает CPU при загрузке; планирование загрузок серий в ночное время на VPS снижает пиковую нагрузку. restart: unless-stopped не создаёт бесконечный restart loop при ошибке конфигурации, если контейнер стабильно падает — администратор увидит статус Exited в docker ps -a и обратится к логам.

Итог практической главы: инфраструктура AniHex превращает набор исходников в воспроизводимый сервис просмотра аниме с сохранением состояния, защищённой сетевой топологией и документированным жизненным циклом от разработки до VPS.

Детальный разбор nginx location для SPA и API. Блок location /api/ с proxy_pass http://api:3001/api/ сохраняет префикс /api на upstream — Express маршруты смонтированы с тем же префиксом. Trailing slash в proxy_pass важен для корректной подстановки URI. Блок /media/ с proxy_buffering off снижает задержку стриминга. Корневой location / с try_files $uri $uri/ /index.html обрабатывает маршруты React Router без серверного рендеринга: любой неизвестный путь отдаёт index.html, клиентский роутер берёт управление. Без этой директивы обновление страницы на /catalog дало бы 404 от nginx.

Связь compose с файлом server/.env.example: при локальной разработке копируется server/.env; в Docker переменные DATABASE_URL и ANIME_DIR переопределяются в compose, поэтому .env на хосте для api-контейнера не монтируется по умолчанию — избегается конфликт localhost с db. Разработчик сервера тестирует логику без Docker с JSON; интеграционное тестирование полного стека — через compose. Такой dual-mode описан в DEPLOY.md и снижает трение между соавторами.

Масштабирование контента: при росте библиотеки аниме каталог docker-data/anime может занять сотни гигабайт. VPS выбирают с запасом диска; ext4/xfs на хосте; мониторинг df -h. Возможна вынесенная NFS или S3-совместимое хранилище с mount в контейнер — вне рамок ВКР, но том docker-data проектируется как единая точка замены backend-хранилища. PostgreSQL при росте нагрузки чтения может получить read replica вне compose — для учебной нагрузки одного инстанса db достаточно.

Юридико-организационный аспект: развёртывание платформы с пользовательским контентом на VPS требует соблюдения политики хостера и авторских прав на размещаемые серии. Инфраструктура не решает правовые вопросы, но обеспечивает контроль администратора через закрытую админку за nginx. Пароли ADMIN_* и отсутствие публикации порта API — элементы технической защиты административного контура.

Приложения к работе содержат листинги docker-compose.yml, Dockerfile, nginx.conf и текст DEPLOY.md в полном объёме из репозитория vite-project. На защите рекомендуется показать живой docker compose ps и дерево docker-data в файловом менеджере для наглядности персистентности. Демонстрация exec в контейнер db с psql опциональна и подтверждает наличие таблиц schema.sql.

Качественные показатели реализации: время холодного старта стека после сборки — порядка 1–3 минут в зависимости от железа; время повторного up без build — менее 30 секунд; размер образа web после multi-stage — существенно меньше, чем образ с Node runtime; отсутствие публикации портов db и api — соответствие рекомендациям OWASP по минимизации поверхности атаки на уровне сети. Количественная оценка сжатия видео зависит от исходников и CRF; инфраструктура обеспечивает наличие ffmpeg в каждом экземпляре api без установки на хост.

Роль обратного прокси в единой точке входа упрощает добавление WAF или rate limiting на уровне nginx в будущем (limit_req_zone). Сейчас лимиты запросов реализованы на API (модуль authLimits.js), но nginx может дополнить защиту от DDoS на границе. Для учебного хостинга базовой конфигурации достаточно.

Заключение

В выпускной квалификационной работе решена задача контейнеризации и автоматизации деплоя сервиса для просмотра японских мультипликационных сериалов на примере платформы AniHex. Теоретически обоснованы преимущества контейнеров перед ручной установкой и полноценными ВМ для трёхзвенного веб-приложения, рассмотрены Docker, Compose, основы CI/CD, роль nginx как reverse proxy и этапы размещения на VPS.

Практически реализованы docker-compose.yml с сервисами db, api и web, Dockerfile API с ffmpeg, multi-stage Dockerfile frontend с nginx, конфигурация deploy/nginx.conf, персистентные тома docker-data, переменные окружения для транскодирования и администрирования, документ DEPLOY.md с описанием запуска, переноса и эксплуатации. Достигнута воспроизводимость окружения, сохранность медиа и базы данных, единая точка входа для пользователя и безопасная изоляция API во внутренней сети Docker.

Работа дополняет разработку серверной логики и клиентского приложения, выполненную соавторами: инфраструктурный слой превращает раздельные артефакты в цельный развёртываемый продукт. Дальнейшее развитие может включать автоматический CI/CD пайплайн, вынос секретов в Docker Secrets или внешнее хранилище, мониторинг и горизонтальное масштабирование за пределами одного VPS.

Таким образом, цель и задачи ВКР выполнены, предложенный контейнерный контур пригоден для демонстрации на защите, переноса между компьютерами и пилотного развёртывания в сети Интернет.

Личный вклад автора ([ФИО одногруппника]) включает проектирование схемы db–api–web, написание и согласование docker-compose.yml, Dockerfile для API и frontend, конфигурации deploy/nginx.conf, организацию томов docker-data, включение ffmpeg в образ API, описание переменных окружения и подготовку руководства DEPLOY.md с разделом о VPS. Прикладной код сервера и клиента разработан соавторами; инфраструктурный слой интегрирует их без изменения бизнес-логики.

Направления дальнейших исследований и внедрения: внедрение полноценного CI/CD с публикацией образов; использование Docker Secrets или внешнего vault; вынос PostgreSQL в управляемый облачный сервис при росте нагрузки; CDN для раздачи /media/; Kubernetes при необходимости нескольких реплик api; observability (Prometheus, Grafana) для мониторинга диска и времени перекодирования. Для текущего масштаба учебной платформы AniHex предложенное решение является достаточным и экономически оправданным.

Сопоставление с аналогами: коммерческие стриминги используют CDN, микросервисы и оркестраторы; учебный AniHex воспроизводит упрощённую трёхзвенную схему, достаточную для понимания принципов. Локальные медиасерверы (Plex, Jellyfin) также используют контейнеры в документации сообществ; подход bind-mount для медиа библиотеки совпадает с практикой docker-data/anime. Отличие — интеграция с веб-каталогом и админским API, а не только сетевой шаринг папки.

Рефлексия по командной работе: разделение «сервер + клиент» / «Docker» позволило параллельную разработку при согласовании контрактов /api и /media и схемы БД. Инфраструктурный автор не блокировал прикладных разработчиков: локальный npm run dev оставался доступен. Финальная интеграция произошла через compose без переписывания прикладного кода — показатель корректного разделения ответственности в команде из двух-трёх человек.

Педагогический эффект выполнения темы: студент осваивает полный путь от теории виртуализации до работающего URL в браузере после одной команды терминала. На защите целесообразно продемонстрировать сравнение «до Docker» (описание ручных шагов) и «после» (live compose up), чтобы комиссия оценила измеримый выигрыш. Документ DEPLOY.md служит не только для команды, но и как приложение к пояснительной записке для проверяющего без доступа к репозиторию.

Итоговая оценка достигнутого уровня автоматизации: сборка и запуск автоматизированы полностью; доставка на VPS полуавтоматическая (git pull + compose); непрерывная интеграция в облаке — резерв на будущее. Термин «автоматизация деплоя» в названии ВКР оправдан сокращением ручных операций с часов до минут и формализацией повторяемого сценария, зафиксированного в docker-compose.yml и DEPLOY.md.

Проверка полноты артефактов инфраструктуры: в репозитории присутствуют docker-compose.yml, server/Dockerfile, корневой Dockerfile, deploy/nginx.conf, DEPLOY.md; каталог docker-data создаётся при первом запуске и документирован как обязательный при переносе; переменные окружения перечислены в compose и DEPLOY.md. Совокупность артефактов закрывает полный жизненный цикл развёртывания учебно-производственной платформы просмотра японских мультипликационных сериалов.
