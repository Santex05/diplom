Откройте `presentation.html` в браузере и прокручивайте вниз по разделам.

## Слайд 2 — Актуальность и проблема

Современный зритель ожидает от аниме-сервиса не только каталог, но и быстрый поиск, фильтры, плеер с запоминанием прогресса и личные списки. Многостраничный сайт с полной перезагрузкой даёт медленные переходы. Одностраничное приложение на React позволяет менять экраны без reload, хранить состояние в контекстах и кэшировать данные на клиенте. Проблема — нужен специализированный UI под аниме-каталог: жанры, OP/ED, очередь просмотра — это не даёт готовый CMS-шаблон.

## Слайд 3 — Цель, задачи, объект

Цель — разработать клиентскую часть веб-платформы AniHex. Задачи: спроектировать маршруты и страницы; реализовать каталог с фильтрами; создать HTML5-видеоплеер; внедрить регистрацию, избранное, коллекцию; оптимизировать UX загрузки. Объект — веб-клиент стриминговой платформы. Предмет — SPA на React с интеграцией REST API. Админ-маршруты в репозитории есть, но в данной работе фокус на интерфейсе для зрителя.

---

## Слайд 4 — Технологии и архитектура SPA

Стек: React 19 для компонентного UI, Vite 8 для сборки и dev-сервера с proxy на /api, React Router 7 для маршрутизации с lazy loading, Tailwind CSS 4 для адаптивной тёмной вёрстки. На диаграмме — BrowserRouter и провайдеры: AuthContext (пользователь и token), AnimeContext (каталог), PlayerUi (состояние плеера), QueueContext (очередь просмотра). Страницы в каталоге pages/ подключаются через Suspense. Данные приходят из api.js — обёртки fetch к REST API сервера; детали endpoints — в работе соавтора по backend.

---

## Слайд 5 — Страницы и маршрутизация

Реализованы маршруты: главная / с баннерами и подборками; /catalog — каталог; /anime/:id — карточка и список серий; /watch/:id/:ep — просмотр; /favorites и /collection — личные разделы; /auth и /profile — вход и профиль. React Router сохраняет URL при фильтрах каталога — ссылку можно отправить другому пользователю с теми же фильтрами. Lazy loading уменьшает начальный bundle: тяжёлые страницы подгружаются по требованию.

---

## Слайд 6 — Каталог и фильтрация

Каталог получает полный список аниме одним запросом GET /api/anime, дальше фильтрация на клиенте — функции filterAnimeList и parseGenresParam в utils/filterAnime.js. Жанры работают по логике AND: выбранные жанры должны все присутствовать у тайтла. Есть фильтры по типу, сезону, году, возрасту, поиск с debounce. При скролле подгружаются порции карточек. При первой загрузке показывается CatalogSkeleton — пользователь видит структуру страницы, а не пустой экран. Диаграмма на слайде: API → apiCache → AnimeContext → filterAnimeList → CatalogPage.

---

## Слайд 7 — Видеоплеер и страница просмотра

Компонент VideoPlayer построен на HTML5 video. Качества берутся из episode_sources, которые приходят с сервера — клиент только переключает source. Реализованы: продолжение с сохранённой позиции; кнопки Skip OP/ED по меткам времени из API; горячие клавиши (пробел, полноэкранный режим, громкость); autoplay next episode; панель PlaybackQueueBar через QueueContext. Страница WatchPage связывает плеер, информацию о серии и навигацию по эпизодам.

---

## Слайд 8 — Авторизация и персональные разделы

AuthPage — регистрация и вход через userApi.js; token сохраняется в localStorage и подставляется в Bearer-заголовок. После login локальное избранное синхронизируется с сервером. FavoritesPage — быстрый доступ к тайтлам. CollectionPage — коллекция с прогрессом просмотра по сериям. RatingBlock на карточке аниме отправляет оценку на API. Валидация форм на клиенте (длина пароля, совпадение подтверждения) снижает число ошибочных запросов до отправки на сервер.

---

## Слайд 9 — UX загрузки и кэш API

Модуль apiCache.js хранит ответы с TTL: каталог 45 секунд, страница аниме 30, баннеры 60. Это уменьшает нагрузку на сервер при переходах между страницами. PageLoader и минимальная задержка показа скелетона делают загрузку визуально стабильной — как на крупных стриминговых сервисах. Компоненты Skeleton используются на главной, в каталоге и карточке аниме.

## Слайд 10 — Тестирование клиентской части

Автотесты: npm run test:client — четыре проверки нормализации жанров в tests/genres.test.js. Линтер: npm run lint для каталога src/. Production-сборка: npm run build формирует статику в dist/. Интеграционное тестирование — вручную по чек-листу: все маршруты, фильтры в URL, resume просмотра, skip OP, autoplay next, синхронизация избранного — при работающем REST API (локально dev:server + dev). Адаптив проверялся на ширинах 360, 768 и 1280 px.

## Возможные вопросы жюри

**Почему React?**  
Широкое распространение, компонентная модель, удобные контексты для глобального состояния SPA.

**Как плеер получает OP/ED?**  
Метки приходят в JSON серии с API; VideoPlayer читает openingStart/End и показывает кнопки пропуска.

**Зачем кэш на клиенте?**  
Меньше повторных GET при навигации — быстрее UI и меньше нагрузка на сервер.

**Почему фильтрация на клиенте, а не на сервере?**  
Каталог учебного масштаба; один запрос + клиентские фильтры дают мгновенный отклик и простой URL с параметрами.

**Где хранится token?**  
localStorage; для SPA с Bearer API — типичный компромисс. Окончательная проверка прав — на сервере.

**Почему не рассказываете про БД и Docker?**  
Это темы соавторов; я потребляю готовый REST API.
